# AI矩阵与三项目分工 v0.1

本文档记录连锁经营部 AI 化发展的工作地图。它不是最终蓝图，而是用于指导 `lann-site`、`lann-dashboard`、工作OS 三个项目的前置工作，确保后续多模型插拔、外部数据接入和业务判断沉淀不各自为政。

## 一、总体判断

AI 矩阵不是一个单一机器人，而是一组围绕王凯日常经营工作的 AI 角色。核心目标是：

1. 把沟通内容变成可追踪事实。
2. 把业务资料变成结构化数据。
3. 把经营数据变成可解释判断。
4. 把判断沉淀成组织知识。
5. 把结果展示成可执行工作台。
6. 保持模型可插拔，不绑定某一家大模型。

一句话定位：

飞书负责捕获和协作，`lann-site` 负责分析和判断，`lann-dashboard` 负责展示和推进，工作OS负责沉淀和复用。

## 二、三个项目分工

### 1. lann-site：业务判断引擎

定位：选址与经营判断的分析层。

主要职责：

- 选址调研报告结构化。
- 候选点位初筛。
- 外部选址情报接入与结构化。
- 租售比分析。
- 现有门店正反样本库。
- 新点位与历史门店对标。
- 经营表现归因。
- 生成选址/经营分析文档。

它回答：

- 这个点位值不值得继续推进？
- 这个门店经营好/差的主要原因是什么？
- 租金压力是否合理？
- 这个候选点位像哪些历史样本？
- 当前资料是否足够做判断？

不负责：

- 展示界面。
- 日常任务流转。
- 加盟商服务流程设计。
- 大量人工沟通记录沉淀。

### 2. lann-dashboard：经营与项目展示工作台

定位：把事实、状态、分析结果展示给人看。

主要职责：

- 点位项目看板。
- 门店经营表现看板。
- 租售比/风险分层展示。
- 候选项目状态追踪。
- 异常门店提醒。
- AI 分析结果展示入口。
- 人工复核入口。

它回答：

- 当前有哪些候选项目？
- 哪些项目资料缺口最大？
- 哪些门店经营异常？
- 哪些点位值得优先复核？
- AI 给出的分析结论是什么？
- 人下一步该处理什么？

不负责：

- 原始业务判断逻辑。
- Prompt 资产管理。
- 判断源沉淀。
- 深度会议复盘。

### 3. 工作OS：判断源与个人/组织知识库

定位：沉淀“为什么这样判断”。

主要职责：

- 重要判断源候选。
- 会议复盘。
- 管理方法论。
- 业务口径。
- AI 协作规则。
- 关键决策记录。
- 经验蒸馏。

它回答：

- 这次判断背后的原则是什么？
- 以后遇到类似情况怎么处理？
- 哪些经验已经被验证？
- 哪些只是临时判断？
- 王凯的业务判断体系如何被复用？

不负责：

- 大量结构化业务明细。
- 日常项目看板。
- BI 数据分析。
- 直接替代飞书业务表。

## 三、AI 角色矩阵

### 1. 信息捕获 AI

数据来源：

- 飞书消息。
- 飞书妙记。
- 飞书文档。
- 微信/电话后的飞书补录。
- 会议纪要。

职责：

- 识别业务对象：门店、点位、商场、加盟商、城市、责任人。
- 提取事实、待办、风险、承诺、时间点。
- 判断是否需要进入 `lann-site`、`lann-dashboard`、工作OS。
- 给内容打标签。

权限：初期只读 + 生成草稿，不自动写飞书业务表。

归属：工作OS + 飞书入口层。

### 2. 工作流参谋 AI

数据来源：

- 飞书待办。
- 飞书消息。
- 飞书妙记和会议复盘。
- `lann-site` 项目日志和资料缺口。
- `lann-dashboard` 项目状态。
- 工作OS 判断源候选。
- 微信/电话后的飞书补录。

职责：

- 把散乱待办按业务对象、项目和事项类型重新编排。
- 识别事项之间的依赖、冲突、重复和组合机会。
- 判断哪些事项只是执行，哪些事项可能改变原有判断。
- 生成“今日事项编排”。
- 提醒哪些事项建议王凯亲自看，哪些可交给别人推进。

边界：

- 不自动修改飞书待办。
- 不自动派发任务。
- 不自动发消息。
- 不替王凯做最终业务决策。

归属：跨项目，第一阶段优先由工作OS承接，后续由 dashboard 展示状态。

### 3. 会议复盘 AI

数据来源：

- 飞书妙记。
- 会议纪要。
- 飞书文档。
- 会后补充说明。

职责：

- 总结会议结论。
- 提取未决问题。
- 提取承诺和下一步动作。
- 判断哪些内容应进入工作OS。
- 判断哪些内容应进入 `lann-site` 或 `lann-dashboard`。

权限：可生成飞书文档；写入工作OS候选按既定规则执行；不直接修改业务表。

归属：工作OS。

### 4. 选址分析 AI

数据来源：

- 扩展管理候选项目表。
- 选址调研报告。
- 外部选址情报。
- 现有门店经营基准。
- 租金/面积/合同数据。
- BI 经营表现。

职责：

- 判断候选点位资料完整度。
- 计算租售比和压力分层。
- 对标历史门店。
- 识别选址风险。
- 生成初筛结论。

典型输出：

- 可进入复核 / 可跟进但需补资料 / 待补资料 / 谨慎 / 不建议。
- 核心证据。
- 缺口字段。
- 下一步动作。
- 相似样本。

权限：可读飞书和 BI；可生成分析文档；写回候选表需确认。

归属：`lann-site`。

### 5. 经营归因 AI

数据来源：

- BI 经营数据。
- 门店租金数据。
- 门店状态。
- 新客、客单、理疗师产值。
- 会议/沟通中的经营事实。

职责：

- 解释门店表现好/差。
- 识别租金压力、新客弱、客单弱、产能弱等问题。
- 建立正向/反向样本。
- 形成经营改善建议。

权限：只读 BI/飞书，可生成报告，不直接改经营数据。

归属：`lann-site` + `lann-dashboard` 展示。

### 6. 外部选址情报 AI

数据来源：

- 地图/POI：高德、百度、腾讯、Google Places 等。
- 新闻与商业动态：新闻、商场公告、商业地产媒体、招商动态。
- 内容与口碑：点评、小红书、抖音、公众号等授权或人工样本渠道。
- 热点与趋势：百度指数、微信指数、本地生活榜单、平台热度信号等可合法获取来源。

职责：

- 围绕候选点位/商场/城市收集外部信号。
- 把外部信号结构化成指标。
- 生成外部情报摘要。
- 标注来源、时间、可信度。
- 输出给选址分析 AI。

边界：

- 不直接输出最终开店判断。
- 不绕登录、不绕反爬、不采集个人隐私。
- 优先官方/授权渠道；没有官方接口时先做人工样本 + 链接归档 + AI 摘要。
- 长期保存摘要、指标、来源链接和时间戳，不长期保存大段平台原文。

归属：`lann-site` 的外部选址情报层。

### 7. 王凯参谋 AI

数据来源：

- `lann-site` 分析结果。
- `lann-dashboard` 状态。
- 工作OS判断源。
- 飞书会议和沟通。
- 当前任务上下文。

职责：

- 把复杂问题压缩成决策选项。
- 提醒前后口径是否冲突。
- 识别“这件事到底该不该做”。
- 给出行动优先级。
- 准备对上/对下沟通材料。

权限：读工作OS、`lann-site`、`lann-dashboard` 结果；生成建议；不直接执行写入动作。

归属：跨项目，但判断源来自工作OS。

### 8. 展示生成 AI

数据来源：

- `lann-dashboard` 数据接口。
- `lann-site` 分析结果。
- 飞书表状态。
- 用户查询。

职责：

- 生成看板说明。
- 自动解释图表。
- 生成筛选后的分析摘要。
- 给 dashboard 页面补充人话解释。

权限：只读 dashboard 数据，生成文本，不改原始数据。

归属：`lann-dashboard`。

## 四、数据流

飞书沟通 / 妙记 / 文档
→ 信息捕获 AI / 会议复盘 AI
→ 工作OS 判断源候选 + 结构化事实
→ `lann-site` 做选址/经营/外部情报分析
→ `lann-dashboard` 展示状态和风险
→ 王凯参谋 AI 生成决策建议
→ 必要时生成飞书文档 / 会议材料 / 复盘记录。

关键原则：

飞书是入口，`lann-site` 是分析，`lann-dashboard` 是呈现，工作OS 是长期记忆。

## 五、外部数据归口

外部数据单独归口为“外部选址情报层”，纳入 `lann-site`，不直接进入 dashboard 或工作OS。

外部数据在选址判断中的地位：

- 内部数据决定经营可行性。
- 外部数据解释机会与风险。

内部数据回答：

- 租售比能不能成立？
- 相似门店表现如何？
- 预期营收是否合理？
- 新客、客单、理疗师产值的参照是多少？

外部数据回答：

- 这里有没有客流和话题？
- 客群是否匹配？
- 周边竞品是否拥挤？
- 商场是否真的有热度？
- 区域未来是否有变化？

优先级：

- P0 硬条件：租金、面积、预期营收、历史样本。
- P1 重要辅助：商场/商圈/竞品/交通/客群。
- P2 风险提示：新闻、热点、社媒内容。

第一阶段外部数据不做大规模抓取。建议先做地图/POI + 新闻，点评/小红书先采用人工样本链接归档 + AI 摘要。

## 六、权限分层

### L1 只读

- 读飞书文档。
- 读飞书多维表。
- 读 BI/API。
- 读本地 staging/export。
- 读工作OS候选资料。

默认允许。

### L2 生成

- 生成分析报告。
- 生成飞书文档。
- 生成本地 CSV/Markdown。
- 生成 dashboard 摘要。
- 生成判断源候选。

默认允许，但要记录来源。

### L3 写入业务系统

- 写飞书多维表字段。
- 修改候选项目状态。
- 创建/变更任务。
- 发飞书消息。
- 写 dashboard 正式数据表。
- 修改工作OS正式判断源。

必须确认。

### L4 高风险

- 删除数据。
- 批量覆盖。
- 修改权限。
- 改密钥。
- 生产部署。
- force push。

必须显式确认，并说明最坏影响。

## 七、模型可插拔原则

不要围绕模型设计系统，要围绕业务任务设计系统。

业务代码不直接依赖某个模型名，而依赖任务：

- `site_candidate_judgement`
- `meeting_recap_extract`
- `ops_root_cause_analysis`
- `external_site_intel`
- `decision_source_distill`

每个任务必须逐步具备：

1. 输入 schema。
2. 输出 schema。
3. prompt 版本。
4. 评测样本。
5. 默认模型。
6. 可替换模型。
7. 失败兜底策略。

## 八、阶段划分

### 第一阶段目标

让 AI 能稳定回答：

这件事是什么、关联哪个业务对象、资料是否足够、下一步该补什么、是否值得王凯看。

第一阶段交付物：

1. AI矩阵与三项目分工 v0.1。
2. AI任务清单 v0.1。
3. 模型可插拔前置规范 v0.1。
4. `lann-site` / `lann-dashboard` / 工作OS 前置工作清单。
5. 第一批 eval 样本设计。

### 第二阶段任务

在同步推进 `lann-site`、`lann-dashboard`、工作OS 三个项目 AI 化前置工作的同时，完成第一阶段目标。

第二阶段开始引入但不急于做重自动化：

- 外部选址情报层。
- 标准 AI 任务接口。
- 可插拔模型执行层。
- 飞书入口层的事实捕获。
- dashboard 对 AI 结果的展示契约。

暂不做：

- 自动回复飞书消息。
- 自动修改飞书表。
- 自动派发任务。
- 自动替王凯做最终业务决策。
- 做统一大平台。
- 一次接入所有模型。
- 复杂 multi-agent 编排。
